# 因子搜索总体架构 V3 提案

> **日期**：2026-10-14<br>
> **状态**：研究方案提案，尚未授权代码实现；不替代或修改 `TECHNICAL.md`、`MERGE_V2_PLAN.md` 中已冻结的规则。<br>
> **目标**：把“能生成有意义的候选”与“能可靠地判断候选”放进同一架构；最终业务目标是提高生产选股流程的 Top1 交易表现。
>
> **文档落位约束**：本文件是应用户本轮要求新建的一次性评审提案，不是第二套长期权威规格。若用户批准其中决策，应把批准的规范写入 `docs/MERGE_V2_PLAN.md`、实现接口与事实写入 `TECHNICAL.md`，随后在本提案顶部标明已 superseded 并指向正式落点；不在两处平行维护同一规则（TECHNICAL §0.6）。

## 一页结论

1. **不推翻整套门控工程。** 保留门控台账、数据边界、G0–G3/G4 诊断、F1 计算、族校验和生产模型外部对照接口；把当前 54 个固定规格重新定位为 **Gate Grid V1 基准候选库**，而不是“门控可能性的完整搜索器”。
2. **修正 0/720 的含义。** 当前 F1v2 的 720 是 **36 个市场门控 × 20 个 `base20` 因子 × `s=+1`**；它不是 54 个市场/行业门控与全部个股因子的联合测试。门控组级 G2/G3 使用的是 `ic124`（124 个 `role=STOCK` 因子的 IC 矩阵），但 F1 条件增量只测了选定的 20 个因子。F1v2 清单不含 14 个行业门控。故 **FDR 0/720 仅表示当前已登记的这组市场交互检验没有成员通过该族校正**，不能推出“所有门控都没用”或“门控架构失败”。
3. **用户的候选集质疑成立。** `base20` 是一个经过筛选的参考面板，不自动代表全部个股特征、当前生产模型的真实输入，或各经济机制的均衡样本。它适合保留为历史比较/探索面板，不应继续作为判断所有门控价值的唯一正式入口。
4. **研究任务不再二分为“个股因子 / 门控因子”。** 改用“数据粒度 × 经济角色 × 使用任务 × 计算/部署能力”的多维分类。Beta、市场状态、行业扩散、横截面 Alpha、流动性与可交易性不应被塞进两个互斥桶。
5. **首要任务是审计研究对象和表达能力，不立即扩容。** Phase 0 的生产 roster、Top20 来源和算子能力审计，与现有 720 结果的**零成本描述性归因**可以并行；归因只生成假设，不决定正式参考面板，也不构成新统计证据。随后再冻结目标假设和数据边界、验证 Beta20 表达能力。
6. **任务 A（状态自身预测）与任务 B（状态调制 Alpha）应并行、互相提供诊断，但 A 不作为 B 的一刀切前置门槛。** 用户的 Top1 目标以 B 为主线，最终经济增量必须在仓库根生产引擎上验证；模型级增量不移回 merge skill。

## 1. 现状事实与结论边界

| 项目 | 当前代码/文件事实 | 不能从中推出什么 |

| Beta 能力 | `evaluator.py` 有固定 60 日 `BETA60`（按本地 `MKT_RET` 计算）和通用 `TS_REGRESS_BETA(y,x,w)` 本地求值实现；`field_catalog.py` 把该算子列为 `LOCAL_ONLY_OPS`，上传会被拦截。`M14_context` 用到 BETA60，但在 opt-in 的文档模板中。 | “能由 evaluator 手工求值”不等于“默认遗传搜索会主动生成 Beta20”，也不等于能上传平台。当前没有证据证明标准模板/变异系统会系统搜索 `TS_REGRESS_BETA(RET1,MKT_RET,20)`。 |

### 对此前表述的明确修正

“当前 54 规格 × 20 因子在正式口径下没有合格候选”不够准确，应改为：

> **当前 F1v2 市场交互族（36 个市场规格 × 20 个已选参考因子，s=+1）在斜率尺下 h3=20/720、联合 FDR=0/720。** 这是这一个族、这一个面板、这条统计口径的结果。G2/G3 另使用 124 个 STOCK 因子的日 IC 作组级统计；行业交互不在 F1v2 720 中。

因此，0/720 是一个重要的**局部否定结果**：当前登记的市场门控与 `base20` 交互没有通过族校正。它要求我们审视条件增量的候选面板和检验独立性，不是推翻搜索器、G2/G3、或所有市场/行业状态变量的证据。

## 2. 对 Kimi / Codex 方案的综合判断

| 提议 | 判断与改进 |
|---|---|
| 特征统一注册、记录血缘与角色 | 方向正确。先把 `field_catalog.py`、`roles.csv`、`base20.json`、门控规格、生产模型输入清单映射成一份**可审计的元数据契约**；不要未核对职责前就再造一套互相冲突的 `feature_registry.py`、`role_annotation.py`。注册表能管理已有特征，不能创造算子或搜索能力。 |
| 门控自身预测（A）与条件增量（B）分开 | 采纳。A 回答状态变量是否预测市场/行业收益或风险；B 回答它能否调制横截面 Alpha。A 可帮助揭示市场方向代理和混杂，但 **A 不显著不能一票否决 B**，B 显著也不等于 A 有择时能力。 |
| 720 项归因作为第一步 | 不设为默认第一步。Codex 的候选集审计优先级正确：先检查 20 个因子从何而来、是否代表实际生产输入、覆盖哪些机制；之后再判断 720 归因能否改变决策。已存在的 0/720 应保留，不因归因选择而重定义。 |
| 用 Beta20 检查搜索表达能力 | 采纳为具体能力验证案例。当前代码能计算一部分 Beta 语义，但默认搜索生成和平台部署能力不同；应分别验收，不能以“注册了 Beta20”冒充“搜索器发现了 Beta20”。 |
| 任务 A 是任务 B 的混杂前置 | 部分采纳其诊断价值，不采纳其统一门槛地位。A 的结果作为 B 的解释变量/混杂诊断，不自动决定 B 是否允许检验。 |
| 分别建族 | 采纳“按假设族管理”，但分文件或分 `family_id` 不等于独立样本。若从 A/B/C 多个任务中择优宣布一个“最优门控”，跨任务选择仍须在设计中计入或用后续独立确认。 |

## 3. 新架构：按研究任务分线、共享特征底座

建议把研究对象从两类扩成四类。主业务路线是 **C 发现 Alpha → B 测条件增量 → 外部生产对照 → E3**；A 与 D 是独立任务/诊断，不是所有候选的必经门。

| 任务 | 研究问题 | 候选与主要输入 | 产出 / 禁止的推断 |
|---|---|---|---|
| **A：市场/行业状态自身预测** | 状态对预注册的未来市场或行业收益、波动、极端下跌等目标是否有预测/风险识别价值？ | `MARKET_DAY` / `SECTOR_DAY` 状态序列；不需要个股 Top20。按目标类型和期限分别预注册。 | 状态预测/风险报告；不自动证明改善 Top1 选股，也不作 B 的统一准入门。 |
| **B：状态对 Alpha 的条件增量（主线）** | 已有横截面选股信号在什么状态下更有效？是否改善实际模型/策略？ | 状态 × **明确界定的 Alpha 参考面板**；分别维护生产模型 roster、机制平衡参考面板和历史 Top20 诊断面板。 | F1 类统计候选 → 外部生产模型基线/增强对照 → Top1/交易指标；不能把 `ΔIC` 或 h3 直接称为模型增量。 |
| **C：个股 Alpha 发现** | 表达式、论文机制、已有因子中是否存在稳定的横截面排序信号？ | 当前 `grammar.py` 机制 GP、外部因子筛选、提案入口、未来的 typed grammar。 | Alpha 候选与时间外验证；Top20 是这条线当前某轮筛选结果，不能不经审查就充当 B 的全体研究对象。 |
| **D：风险暴露 / 风险控制 / 流动性与执行** | 暴露或状态能否估计风险、控制仓位、改善可交易性？例如 Beta、特质波动、流动性压力、可交易性状态。 | STOCK / MARKET / SECTOR 不同粒度的暴露与风险变量；目标与 A/B 不同。 | 风险/执行约束与诊断；除非另行定义 Alpha 排序目标，不把 Beta 等风险暴露强行按普通 Alpha 的 IC 规则判生死。 |

**主线裁定建议**：既然最终业务目标是 Top1 交易改善，把 B 设为主要的门控效用问题；A 并行作为市场时序/方向代理诊断；C 继续负责产生更广的 Alpha 候选；D 管理 Beta 与可交易风险。A、B 的候选输出可以共同进入同一后续决策，但它们不互相冒充证据。

## 4. 从“因子类型”升级为多维特征本体

不要把 feature 作为单一 `STOCK` 或 `GATE` 枚举。一个特征应由多个正交属性描述，同一特征可在不同任务中有多个使用角色。

| 维度 | 推荐字段/值 | 例子 |
|---|---|---|
| **数据粒度 / 实体** | `STOCK×DATE`、`SECTOR×DATE`、`MARKET×DATE`、`CROSS_SECTION×DATE`、事件/横截面掩码 | `BETA20` 是股票×日；`MKT_RET` 是市场×日；`DISP` 可是行业×日并广播到股票。 |
| **经济语义** | `CROSS_SECTIONAL_ALPHA`、`MARKET_EXPOSURE`、`SECTOR_EXPOSURE`、`RISK_VOL_DRAWDOWN`、`REGIME_STATE`、`FLOW_LIQUIDITY`、`TRADABILITY`、`EVENT_ELIGIBILITY`、`RELATIVE_RESIDUAL` | Beta20 = 市场暴露/风险，不因可排序就自动成为 Alpha；行业收益排名 = 行业状态。 |
| **可承担任务** | `RANK_STOCKS`、`PREDICT_MARKET`、`CONDITION_ALPHA`、`CONTROL_RISK`、`FILTER_TRADABILITY`、`EXECUTION_DIAGNOSTIC` | `MKT_RET` 可用于市场预测或作为调制条件；只有在横截面定义合法时才可用于选股排序。 |
| **计算范围 / 广播方式** | 面板键、聚合实体、点时行业映射、是否广播、有效截面数 | 行业状态广播给成员股时，有效统计样本不能误当成股票总数。 |
| **时序与单位契约** | 输入字段、信号时间、可用时间、复权/基准定义、单位、窗口、warm-up、缺失/零方差规则 | `BETA20` 必须声明基准收益具体定义（当前 `MKT_RET` 是本地全市场等权 `RET1`），而不只记“市场 Beta”。 |
| **计算/搜索/部署能力** | `evaluator_supported`、`grammar_generated`、`unit_tested`、`platform_verified`、`uploadable`、`production_model_accepted` | `TS_REGRESS_BETA` 当前可本地求值、属 LOCAL_ONLY，不能据此标为平台可上传。 |
| **身份与实验血缘** | feature definition/version、数据源声明、窗口/标签/切点、family/task manifest、运行配置哈希 | 区分“特征定义相同”和“在新数据/新标签上测过”；数据版本是溯源信息，评估合同要记录实际数据边界。 |

`roles.csv` 的六类现有分类是有用的初始标签，保留并映射到新维度；升级不是把六类继续扩成几十个互斥类，而是避免**粒度、语义角色、下游用途、是否能搜索/上传**互相替代。

## 5. 搜索表达能力：从固定网格升级为有类型约束的机制搜索

### 5.1 当前门控方案的定位

54 个基础量×操作化规格作为 **Gate Grid V1** 保留，作用是：

- 对已有候选基准可复现；
- 检查当前 G0/G2/G3/F1 管线的统计与工程行为；
- 为下一版机制搜索提供种子、对照和近克隆基准。

它不是“全部门控因子”。它覆盖了有限的方向中性市场/行业摘要量及四种时间操作化；没有系统表达股票级动态暴露、成分关系、横截面/时序交互、软状态转换，也没有把所有 QWIN 与转换组合展开。旧 M1–M4/S1–S3' 定义不恢复；旧定义已被用户裁定删除，其失败教训保留为约束。

### 5.2 新门控/调制搜索的候选结构

以带类型的 AST/计算图表示候选，而不是任意拼接字段。每个节点注明实体粒度与输出类型：

```text
可用原始量/已注册特征
  → 粒度内变换（滚动均值/波动/趋势/分位/变化/相关/回归）
  → 参照变换（自身历史分位、同日市场/行业横截面排名、行业相对量）
  → 状态表达（连续权重、预注册阈值、平滑开关/分段状态）
  → 用途：状态预测 / 风险控制 / 与 Alpha 交互
```

候选机制至少按以下轴维护配额和覆盖图，而非只看生成总条数：

1. **市场**：广度/扩散、横截面离散、领导股集中、波动/尾部、流动性/资金流、大小盘/风格轮动。
2. **行业**：行业间领导/轮动、行业内离散、行业成交拥挤、行业相对市场强弱、行业风险扩散。
3. **股票级状态/暴露**：滚动 Beta、特质波动、残差动量/残差风险、个股流动性/跳空压力；这是当前 market/sector 两类没有覆盖的第三粒度。
4. **Alpha 条件形态**：连续调制、仅开仓/弃权门、两态/多态、行业内条件；每一种作用形式是独立研究定义，不是同一个 `form` 的无代价变体。

新生成器采用“机制模板种子 + 受约束变异/组合 + 固定预算”的混合方式：每个候选都能追溯到机制、输入、算子和参数；按机制给探索预算；先作不看标签的类型/缺失/稀疏/时间因果检查，再进入目标相关的发现评估；使用值指纹、秩指纹和结构指纹去重，但去重结果仅作为候选管理，不以相关高就宣称机制等价。

**不建议**把新基础量、窗口、转换、阈值、方向、标签、目标无约束笛卡尔积。扩容应按机制覆盖缺口提出；预先限制每种参数化的主值，登记版本和全部生成/拒绝事件。`--limit-gates` 继续是调试/分批控制，不是科学检验族边界。

### 5.3 算子增强路线与 Beta20 验证

当前能力应按“能算 / 能生成 / 能平台运行”分开：

| 能力层 | Beta20 当前状态 | 下一步 |
|---|---|---|
| 本地计算 | `ensure_local_fields()` 计算固定 60 日 BETA60；`TS_REGRESS_BETA(y,x,w)` 有通用本地求值路径。 | 用可控合成数据和独立 reference 实现验证 cov/var、滚动边界、全窗 warm-up、零方差、停牌/缺失、股票分组与无未来数据；再比较 `TS_REGRESS_BETA(RET1,MKT_RET,20)` 与独立 Beta20 实现。 |
| 默认候选生成 | 默认 `TEMPLATES` 以已验证算子为主；M14 是 opt-in 本地上下文模板，使用 BETA60；没有足够证据说明标准变异会系统探索 Beta20。 | 通过能力测试后新增明确的 `EXPOSURE_BETA` 种子/模板，使 Beta20 可被生成、记录、评估；同时保留 BETA60 作基准。 |
| 平台上传 | `TS_REGRESS_BETA` 和 `MKT_RET` 属本地专用，`formula_uses_local` 阻止含本地项公式上传。 | 默认保持 local-only。只有平台确有等价字段/算子并完成平台冒烟，才能单独提升 uploadable 能力；不得把本地 Beta 包装成平台原生公式。 |

**粒度约束**：Beta20 是 `STOCK×DATE` 的暴露，不是每日所有股票共享的 `MARKET×DATE` 广播门。通过 Phase 2 后可以进入风险/暴露任务；若研究它与 Alpha 的交互，必须作为股票级条件调制另定 estimand、推断单位和 family，不能直接并入现有市场门控 F1v2 族。

算子实现/开放顺序：

1. **优先补表达能力而非算子数量**：打通 `RET1`、明确基准收益、Beta20/60、回归残差；必要时在 typed grammar 中增加受控 template。
2. **补跨粒度安全算子**：股票→行业/市场聚合、点时行业映射、同日横截面排名；输出必须保留样本键与实体数，行业序列的置换/重采样按日期保留整块横截面。
3. **再开放状态变换**：稳健滚动分位、状态阈值、软门/多段状态、趋势/变化/加速度。把参数范围、warm-up 和缺失规则放入 operator contract。
4. **每个算子分开登记能力**：本地实现存在 ≠ 语义测试通过 ≠ 进搜索生成 ≠ 平台已验证 ≠ 生产模型接受。`VERIFIED_OPS` 不能承担所有这些含义。

## 6. 条件增量的参考因子面板：让 B 回答真正的问题

### 6.1 三种面板、三种结论

| 面板 | 用途 | 推荐地位 |
|---|---|---|
| **ProductionRoster**：实际生产模型版本的输入特征清单 | 直接回答“这个状态/交互能否改善当前生产模型的 Top1/风险/收益” | 如果目标是改善现行生产系统，这是 B 的主要经济验证面板；先从 `main_alpha_stage15_hp_search.py` 当前配置审计并冻结，不用 `roles.csv` 或 Top20 代替。 |
| **MechanismBalancedReference**：从已登记个股特征库按经济机制分层选取的代表面板 | 研究门控条件效应能否跨不同类型 Alpha 迁移 | 主要统计参考面板。选择规则基于定义、来源、质量和冗余，不按同一待检验期间的排名挑选。成员/机制配额必须先冻结。 |
| **HistoricalTop20**：现有 `base20.json` / F1v2 成员 | 复现已有结果、比较历史与新版设计 | 保留为探索/历史基准，不作为门控全体价值的唯一正式标准。 |

`roles.csv` 的 124 个 STOCK 列是可用因子目录，不等于实际模型 roster，也不自动适合作为 124×所有门控的确认族。不能从“Top20 太窄”直接跳到“把 124 全部与所有门控做笛卡尔积”：先审计因子来源、语义、冗余、模型使用状态与数据窗口，再明确要回答的是泛化条件效应还是生产模型增量。

**ProductionRoster 是经济验证对象，不天然是无偏统计确认面板。** 如果这些特征或模型版本曾用同一历史区间反复搜索、挑选或调参，在该区间上的门控交互结果仍属探索性/条件性证据。真正确认需要冻结后未参与这条选择链的数据。

### 6.1.1 新搜出的个股因子如何进入后续面板

面板允许随 Alpha 搜索演进，但**不随结果自动滚动扩张**。对每个新因子按以下规则处理：

1. 先作为 Alpha 候选独立登记，核实经济语义、计算/点时正确性、有效覆盖、来源和冗余；不能因为它与某门控的交互显著才准入参考面板。
2. 若它是真实生产模型的新输入，进入带版本号的 `ProductionRoster_vN`；该 roster 上的历史交互试验仍按实际数据接触标记，不自动成为确认性证据。
3. 若它填补了机制平衡参考面板的预注册覆盖缺口，只有在**查看本轮门控交互结果之前**按固定准入规则加入下一版本 `MechanismBalancedReference_vN`。
4. 新成员进入新 panel/family 版本；旧 family、旧成员哈希和旧结论保持不变。不得将新搜出的因子追加到旧清单后沿用旧 FDR 分母。
5. 若成员增添/更换是看过当前门控交互结果后的决定，新面板仍可用于后续探索；确认结论须等新的未触碰数据或明确覆盖整个适应选择链的设计。

因此答案不是“永远用旧 Top20”，也不是“每搜到一个因子就立刻加入门控评估”。新因子可以进入后续研究，但经由**明确准入规则、面板版本和新检验族**进入。

### 6.2 F1 统计量要与部署动作对齐

当前定义 `F1=d·x·max(s·g,0)` 是**单侧正部加权/关门弃权**的策略形式。即使 `g=2p−1` 连续，`max(s·g,0)` 仍不是对完整连续状态的对称线性调节；G2 中的 `RankIC_t=a+b·g_t+e_t` 斜率与 F1 的正部交互估计的是不同对象。

新一轮必须在看结果前明确 B 的主 estimand：

- **若产品动作是低状态弃权、高状态启用 Alpha**：保留正部门控为主候选，把阈值/门控方向/权重形式预注册；
- **若问题是状态如何连续改变 Alpha 能力**：把完整连续交互（例如 Alpha×中心化状态）的斜率/边际效应定为主估计量；单侧开关作为另一种策略假设；
- **若问题是 Top1 交易改善**：统计交互指标只作筛选层，最终主终点在生产模型对照中冻结。

这些形式不能在结果出来后选最好者再称“斜率尺”。多种形式都试时，必须加入候选家族/预注册或在全新确认段验证。

## 7. 评估、筛选与证据层级

### 7.1 共享的管道骨架

```text
注册特征与数据契约
  → 按任务生成候选（Alpha / 状态预测 / 条件调制 / 风险执行）
  → 结构、类型、因果、缺失、覆盖和重复检查（不看结果标签）
  → discovery 搜索/低成本筛选（只用于选择候选）
  → 冻结成员 + estimand + 数据窗 + 算法 + 族清单
  → confirmatory 统计检验（未被选择流程看过的数据；或明示 E1 探索性）
  → 生产模型/交易经济对照（merge 外）
  → 冻结候选与配置，之后才有资格积累 E3 前向确认
```

### 7.2 各层的职权

| 层 | 应回答 | 应做 | 不应做 |
|---|---|---|---|
| **工程/类型** | 候选是否定义完整、无前视、可求值、粒度合法？ | AST/type check、单位/范围、warm-up/coverage、点时映射、panel/hash 血缘、语义测试。 | 用 IC/p 值判断合法性，或因统计结果改数据契约。 |
| **廉价候选筛选** | 哪些候选明显退化、错误或无覆盖？ | G0/稀疏/结构/排序等价检查；候选数大时进行发现集排序。 | 把同一发现集上被 G2/G3 选中的候选，再当作未经选择的确认集。 |
| **任务 A：状态自身评估** | 市场/行业状态对预注册未来目标是否有效？ | 按市场日或日期×行业的正确抽样单位，用块法/NW/聚类处理时间和横截面依赖；目标、期限单独声明。 | 用个股 Top20 作为必要输入；把 A 的不显著当成 B 的禁入。 |
| **任务 B：条件增量** | 预定义 Alpha 面板在状态条件下是否改善？ | 对冻结的 alpha/gate/形式/方向/窗口全族评估；报告 h3、CI、块稳定、placebo、FDR，另报不同门控家族相关性。 | 只保留当前 Top20 后宣称代表全体 Alpha；只报名义通过者；把 `ΔIC` 叫作模型增量。 |
| **经济/模型对照** | 加入特征或状态策略是否真正改善生产目标？ | 由生产引擎做基线/增强成对实验，冻结同一数据、特征 roster、训练预算/折、掩码和交易成本；报告 Top1 净收益、回撤、换手、交易数、稳定性。 | 把 LightGBM/模型增量诊断移进 merge skill；改变冠军超参来迁就新增候选。 |
| **前向确认 E3** | 冻结流程在完全未参与选择的数据上是否保留效果？ | 冻结模型/特征/任务定义后，等标签成熟后运行；保留独立事件日志。 | 用已在搜索或 holdout 排名中参与决策的日期称“独立前向”。 |

### 7.3 `h3`、FDR 与检验族

- `h3_pass` 当前是三项名义规则的合取（CI 下界、至少 4/6 块为正、placebo p<0.05）；它不是一个独立流水线阶段，也不等于校正后显著。
- `judge_f1.py` 当前对输入族中的 `placebo_p` 做 BH-FDR，另存 `fdr_q/fdr_sig`。结果应同时报告 **h3** 和 **FDR**，并明确 S8 资格要求是否二者都必须满足。
- 多重检验族应至少绑定：任务、候选 ID/定义 hash、市场/行业/股票粒度、Alpha 面板版本、方向、门控形式、阈值/窗口/QWIN、标签与期限、估计量、置换/块设定、时间边界、清单版本。当前 `members_hash=(gate,base,s)` 是成员校验，不是完整研究设计哈希。
- 如果在同一数据上先用 G2/G3、rank/topn、人工查看结果挑候选，再只对幸存者做 F1，F1 的名义族 FDR **不会自动校正这整条自适应选择链**。正式办法二选一：
  1. discovery 阶段允许自适应选门控；冻结后在未参与挑选的 confirm 时间段，对冻结成员运行确认族；或
  2. 对全部实际被选择/比较的检验整体计入确认规则（计算成本更高），不把前置筛选当作免费。
- A/B/C/D 可有各自问题明确的族清单，但共用数据且最终跨任务择优时不能宣称统计独立。跨任务的“挑最终赢家”要么在总设计里控制，要么只作发现并交给独立前向段确认。
- `f1_family.py` 的成员逐一对应与哈希约束值得保留并拓展；新设计不应通过拆成多个小 manifest 来规避整体搜索的多重性。

### 7.4 市场、行业、股票级状态的不同统计单位

- **市场级**：`g_t` 是每日一个值；时间日期是核心独立抽样轴，使用保留时间依赖的重采样。
- **行业级**：`g_{s,t}` 是日期×行业面板；同日行业受共同市场冲击。重采样应以日期块为单位并保留该日完整行业向量；行业成员变化和行业映射必须点时定义。不能把 131 个行业在同一天当作 131 个独立日期。
- **股票级暴露**：`g_{i,t}` 可因股而异（如 Beta20），不等于市场广播门。条件增量的估计样本、聚类方式、截面可比性需单独设计。
- **方向/收益代理诊断**：只对 B 的条件效应解释是否被市场方向/风险暴露解释；不能以“所有状态必须方向中性”抹掉任务 A 中本来允许方向性的择时/风险目标。

### 7.5 实用效应下限与门控级汇总

**实用性需要预注册，但不采用未经校准的硬阈值。** 统计显著不等于交易上有价值；反过来，在未将 `ΔIC` 与 Top1 的经济收益建立稳定映射前，也不能凭空规定“`ΔIC<0.02` 就淘汰”。

- Phase 1 应提出并验证一个可解释的最小实用效应（MDE）：优先在外部生产对照指标中定义（Top1 净增量、回撤/换手约束等）；若要把它投影到 F1 的 `ΔIC` 单位，必须用预先冻结的映射/历史仿真标定，并记录不确定性。
- 若校准完成，可在确认设计中预注册 futility 规则：例如估计区间上界仍低于该 MDE 时，判为“达不到预定义实用价值”，而不是改写为“统计上不存在效应”。**未校准 MDE 时只报告效应与区间，不在 `judge_f1` 中加任意数值硬门。**
- **Pair 级口径**（gate×alpha）继续回答“哪些具体组合有效”；另预注册一个 **gate 级面板汇总 estimand**，回答“该门控是否对预定义面板整体有一致价值”。汇总应先按机制报告，再给面板级 summary；同一日期块对所有因子共同重采样，以保留因子间相关性。
- Pair 级与 gate 级结果并列，不把高度相关的 Alpha 当作独立选票；不使用未经校准的 Fisher 合并或简单计数代替依赖结构。确认前需冻结 effect 标准化、因子面板权重/机制权重、缺失规则、门控级族范围和重采样方法。
- Gate 级“面板总体效应”只对**该固定面板**成立；MechanismBalancedReference 的样本代表性有限时，不外推成“对全部未来 Alpha 有效”。

### Phase 0：事实审计（不新增确认性实验、不扩容）

1. 从生产训练脚本实际配置列出当前模型每个输入特征、来源、训练中是否启用、特征变换和点时可用时间；区分“注册表 124 STOCK”“Top20”“生产 roster”。

4. 给现有产物加研究状态标记：F1v2 = “历史 base20 市场交互族”；FDR 0/720 保留；14 个 sector gate 与此族分开注明；所有当前结论按 Case B/E1 解释。

6. **审计版本控制与大文件治理**：记录 Git 根目录、branch/remote 状态、staged/unstaged 改动、已跟踪大文件（包含 parquet/log、生成图表、`.venv`）和 `.gitignore` 与 index 的差异；区分“工作区当前已忽略”与“历史提交仍保存 blob”。代码、小型研究规格、面板 roster、审计表、可复现 manifest 和经验证的依赖锁应作为版本化候选；行情/因子 parquet 与大型派生产物由明确的数据存储负责，Git 只记录版本声明/路径/校验和。移除 `.venv` 跟踪前，须先有可复建且已验证的依赖清单；审计阶段不自动提交、不删除本地文件、不重写历史。
7. **审计确认数据是否真的未被读取**：逐一列出 cache、`factors.parquet`、labels、门控面板、Stage15 生产入口的实际读路径和日期限制；核对 `boundary.py`、`run_search`/`evaluator.load_panel` 等非统一入口。`windows.py` 当前记载 E3 首个信号日为 2026-09-21、标签可用日上界为 2026-09-18；这只作为待核的既定边界，必须先审计历史访问日志，不能仅凭日期声明它“未触碰”。

**验收**：实际生产 roster、base20 来历、124 列作用、Beta20 能力矩阵、市场/行业 family 覆盖、Git 中大文件的当前/历史状态均能从文件与脚本追溯；描述性归因只形成可检查的假设；未满足前不扩族、不把 720 归因结果包装为总门控结论。

### Phase 1：冻结目标与特征本体（仅规格决策）

1. 主业务目标声明为 B（状态条件下的 Alpha/生产 Top1 增量）；A 与 D 独立报告，不作为前置门。
2. 冻结 B 的主参考面板：**优先选实际生产 roster 作经济验证**；同时建立不按当前期 IC 排名的 MechanismBalancedReference 作研究面板；Top20 保留为历史/探索对照。
3. 冻结可部署动作：一侧弃权门、连续交互或多态切换中选定一个主定义；备选定义列入同一候选/确认策略，不准结果后挑形式。
4. 先映射现有 roles/field catalog/schema；再决定需要一个单一 registry 文件还是代码 API，避免双重事实源。
5. 明确 MDE / practical significance：先在经济结果定义实用下限；仅在能用冻结方法把它映射到 F1 `ΔIC` 时才设置 F1 futility 门。没有可靠映射就不加 F1 数值硬门。
6. 冻结 pair-level 与 gate-level 的主次关系：pair-level 作为具体交互定位；gate-level 汇总作为固定面板上的整体效应判断，预先决定哪个参与确认、如何按机制汇总和如何保留因子间依赖。
7. **冻结确认数据池**：分别记录 discovery 信号日上界、确认池首个信号日、确认池可用范围与 `label_available_max`；核实 2026-09-21 是否仍可作为 E3 起点。在确认协议冻结并授权前，确认/前向池对 discovery、搜索、资格、排名和诊断默认不可读。新数据到达后也先封存，不因日常缓存刷新自动进入搜索。

**验收**：每类特征有实体粒度、语义角色、时间可用性、算子/部署后端；每个任务有目标、候选范围、主估计量、淘汰条件和族边界；MDE 的来源或“不设 F1 实用性硬门”的理由有记录；pair/gate 级主次和依赖处理已经冻结；确认数据边界与默认拒绝/授权机制明确。所有 discovery 读路径默认不能读封存池；确认流程须携带冻结 manifest、任务用途和标签成熟边界，访问事件可审计。

### Phase 2：能力原型（先 Beta20，不直接上线）

1. 按已冻结的 market benchmark 定义验证 `TS_REGRESS_BETA(RET1, MKT_RET, 20)`；分别对比等权 `MKT_RET`、用户认可的市场基准和 BETA60。
2. 在小型合成夹具上验证真实 Beta、常量基准、零方差、缺失、首个有效日、滞后对齐、点时性；与独立 numpy/pandas reference 逐值对拍。
3. 接入独立 `EXPOSURE_BETA` 机制模板/候选 ID；本地研究，标注 `LOCAL_ONLY`；明确不走平台上传。
4. 再验证搜索实际能生成该 AST、台账能保存它的定义和数据边界、快评/全量行为一致。只要任一项失败，结论写“可计算但不可搜索/不可上传”，不模糊成“支持 Beta”。

**验收**：Beta20 的定义、基准、缺失和窗口规则均冻结；合成/随机取值正确；语法生成可重现；本地/平台边界明确。

### Phase 3：门控生成器 V2（旧 54 作为对照种子）

1. 扩充 market/sector/stock 三种状态粒度；把 Gate Grid V1 纳入种子/基线，不删历史数据、不重用其结果为新族。
2. 在类型系统中开放已通过 Phase 2 测试的 rolling exposure、残差、稳健统计和跨粒度聚合节点；每个 operator 有成本估计与 `min_periods` / warm-up / null 规则。
3. 按机制配额生成、去重、记录，先跑标签盲的结构闸；只让确定性的大规模重复或数据/数学错误被硬拒，探索效果弱的候选记录为低优先级而非改写其身份。
4. `QWIN`、窗口、form、正负方向均进入 candidate/experiment identity；变更产生新实验版本，不在旧 54 中悄悄覆盖。

**验收**：生成器能证明每个候选来自哪个机制/AST/窗；相同输入确定性复现；市场/行业/股票粒度与候选输出一致；扩空间数量和统计预算可事先计算。

### Phase 4：Task A / B 独立预注册和 discovery-confirm 流程

1. A 的科学问题与 B 独立，但初始执行**限于 B shortlist 的方向/收益代理混杂诊断**；不在本轮启动全市场择时/风险全量搜索。若以后要独立经营 A，另行冻结目标、预算和家族。
2. B 声明 ProductionRoster 与 MechanismBalancedReference 的先后级别；Top20 只作为探索基准。定义市场/行业/股票级状态对应的 estimand 和推断单位。
3. 对发现数据允许低成本 G2/G3、排名和 UCB；这些结果标 discovery。冻结候选与 complete family manifest 后，才跑确认数据；无未触碰数据时不作确认性结论。
4. 预注册确认族的所有实际候选及参数，成员严格校验，固定 BH/块法、方向、label、cut、阈值、MDE（如已校准）和处理缺失。F1 单侧门控与连续斜率作为不同假设处理。
5. 对 placebo-p/FDR 做 family 级校准测试：在覆盖候选相关性与时间依赖的零效应模拟下检查 p 值校准和名义 FDR 行为。若所选 BH 的依赖假设不足，须在看真实候选确认结果前选择并冻结适用的替代控制法；不能以“用了 BH”代替校准证据。
6. 在**合成面板**上注入已知强度的条件效应，覆盖零效应与多个正/负效应量级、时间自相关、门控/因子相关、缺失和不同实体粒度；估计各 estimand 的检出率、偏差、区间覆盖率及 family-level FDR。效应网格应围绕 Phase 1 冻结的实用效应范围，而非看真实候选结果后挑选；功效模拟只验证仪器，不替代真实样本外确认。

**验收**：发现数据上产生候选后，确认过程不修改族、方向、门限、窗或标签；能完整统计生成、筛掉、确认的各级候选；没有“选中少数行后再把那几行当全集”的断链。

### Phase 5：经济对照与前向

1. 对统计确认的 B 候选，由外部生产引擎作同配置 baseline vs baseline+candidate（或事先定义的 state-conditioned policy）对照；固定训练/验证折、交易掩码、参数预算、成本和输出指标。
2. Top1 净增量、最大回撤、换手/交易数、折间稳定性是经济验收指标；某个 gate 自己预测市场收益不能替代这些结果。
3. 冻结候选、特征定义、模型配置和准入理由后，等待完全未参与筛选的 E3 数据；只有 E3 可被标作前向确认。

**验收**：工程、统计、经济、前向状态分别记录；任何一层不能越级改写另一层的结论。模型级增量继续在 merge 外运行，遵守“不把 LightGBM 模型增量诊断加进 merge skill”的用户裁定。

### 执行防漂移约束

- **Owner**：研究负责人（用户）决定目标、生产面板用途及确认口径；实现/审计执行者给出可追溯的文件、代码和日志证据；实际生产模型负责人提供并确认版本化 roster。没有 roster 负责人确认时，不得把 `ProductionRoster` 当成已冻结事实。

- **阶段闸门**：Phase 0/1 未完成，不进入新生成器实现；Phase 2 Beta20 语义/生成验收未通过，不开放该特征家族；确认样本不存在时，结果标探索性，不以开发样本临时代替。

- **Git 变更保护**：确认 `.gitignore`、index 和历史的差异后，再分别决定“取消跟踪但保留工作文件”与“清理历史 blob”是否必要。后者需要完整备份、远端/协作者协调和单独授权；不得把首次 commit、历史重写或 force push 混入研究 Phase 0 的自动验收。
