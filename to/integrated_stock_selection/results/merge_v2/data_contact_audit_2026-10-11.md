## 1. 已确认事实

### 1.1 个股进化搜索线的窗口（硬编码，不来自 `windows.py`）

`fitness.py:29-31`：

```python
START        = '20210901'   # 2021-09-01
END          = '20260821'   # 2026-08-21
HOLDOUT_START = '20250701'  # 2025-07-01
```

- **[已确认]** `windows.py` 被 18 个门控侧模块 import，**`fitness.py` / `run_search.py`
  均不 import 它**。项目文档所称"窗口单一事实源"**只对门控线成立**。
- **[已确认]** 由此产生两套窗口：进化线 `2021-09-01 ~ 2026-08-21`；
  门控线 `2021-06-01 ~ 2025-12-31`。

### 1.2 两级评估的窗口（用台账 `n_periods` 反算验证）

`DataContext(cycle=3)`，`n_periods ≈ 交易日数 / 3`。台账实测：

| 事件 | n_periods | ×3 | 对应窗 | 面板实测交易日 | 偏差 |
|---|---|---|---|---|---|
| `fast`（抽样 1800 只） | 161 | 483 | `END-24月` = 2024-08-21 ~ 2026-08-21 | 485 | 0.4% |
| `local`（全量，层2） | 402 | 1206 | `START ~ END` = 2021-09-01 ~ 2026-08-21 | 1224 | 1.5% |
| `holdout` | 83 | 249 | 见 1.3 | 280 | — |

- **[已确认]** 一级快评窗 = **2024-08-21 ~ 2026-08-21**，其中
  **280/485 = 58% 落在 holdout（2025-07-01 起）之内**。
- **[已确认]** 二级全量窗 = **2021-09-01 ~ 2026-08-21**（全部 5126 只股票，不抽样）。

### 1.3 holdout 实际评估到 2026-07 —— 决定性证据

`ledger.jsonl` 的 6 条 `holdout` 事件（`created_at` = 2026-09-15）均含
`monthly_excess`，**月度明细直接暴露实际评估区间**：

```

候选 75ee297a40fa (M3_distribution)  同上
候选 e9068973f122 (M5_trend)         同上

候选 5ba7fdecdf12 (M4_location)      同上
```

**[已确认]** 进化搜索的 holdout **读取并评估了 2026-01 ~ 2026-07 共 7 个月的数据**，
且月度超额收益被写入台账、进入 `decision` 事件（含 `axis_corr` 等）→ **结果可被人看到**
→ **[推断]** 该数据已参与候选保留判断。推导链：`rank_score` 用
`min(train_sia, holdout_sia)`（`fitness.py:296-297`）→ holdout 的 SiA 进排序分 →
排序分决定精英保留与撒种 + `monitoring` 事件回写 → 满足"数据影响选择"的定义。

### 1.5 门控线的实际接触（边界记录）

`boundary_log.jsonl` 的 `read_labels` 上界分布（**标签才是判定约束**）：

| 标签上界 | 条数 | 含义 |
|---|---|---|
| 2025-12-31 | 76 | 现行选择窗 |
| 2024-12-26 | 36 | 旧窗（历史运行） |
| **2026-09-18** | **5** | **label = `selftest`×4、`dbg`×1** |

- **[已确认]** 门控线的**评估类**读取（G2/G3、F1、H2、稳定性）标签上界均为
  `≤2025-12-31`，**未使用 2026 年数据做门控判定**。
- **[已确认]** 仅 5 条工程自检读取（`selftest` / `dbg`）把标签读到 2026-09-18。
- **[已确认]** 多处 `read_factors(data_max=LABEL_MAX_DATE)` 读宽后用
  `m = m[m["date"] <= CUT]` 收窄（如 `gate_g2g3_sector.py:72-76`）→
  **因子值读宽、使用收窄**。属数据最小化瑕疵，非判定污染。
- **[待核实]** 上述 5 条 `selftest`/`dbg` 读取是否只用于接口连通性检查、
  是否产生过任何影响选择的输出。

### 1.6 `windows.py` 中 `LEGACY_SEARCH_*` 的出处与搜索线无关

`windows.py:44-47` 记载：

```python
#: 已完成搜索实际使用的历史窗口（由 boundary_log.jsonl 153 条读取记录反查，
#: 全部 label_max=2024-12-26）。保留此常量以便审计"旧结果属于哪段数据"。
```

- **[已确认]** 现 `boundary_log.jsonl` 中 `data_max=2024-12-26` 的记录仅 **10 条**，
  其 label 为 `selftest-neg` / `audit-dir` / `h3calib` / `dbg2`~`dbg5` / `calib2` / `m4diag`
  —— **全是门控与诊断线，无一条来自进化搜索**。
- **[已确认]** `boundary_log.jsonl` **不含任何 `run_search` 记录**（无搜索侧 label）。
- **[推断]** `LEGACY_SEARCH_*` 的命名与注释**指向了错误的对象**：它记录的实际是
  门控/诊断线的读取行为，而非"已完成搜索"的窗口。该常量用于审计"旧结果属于哪段数据"

### 1.7 `END = 2026-08-21` 缺少依据

- **[已确认]** 面板数据实际到 **2026-09-18**（`factors.parquet`，6,272,523 行，1289 交易日）。
- **[已确认]** 标签最长前瞻为 **5 个交易日**（`prodlabel.py:54-55` 用 `shift(-5)`，
  `sell5 = 0.7*gtp.shift(-4) + 0.3*gtp.shift(-5)`）。
- **[推断]** 最后一个标签完整的信号日应为 **2026-09-11**
  （与 `windows.SIGNAL_MAX_DATE` 一致），而非 `2026-08-21`。`END` 比该日**早 15 个交易日**，
  比数据末**早 20 个交易日**。
- **[已确认]** `windows.py:73` `TRUNCATION_WINDOW = ("2026-07-29", "2026-09-11")`，
  `END=2026-08-21` **落在该截断窗内部**。
- **[待核实]** `END=2026-08-21` 的引入时间、配置来源与设计理由。**现有制品无法追溯**
  （无 git、无备份副本、无运行记录）；唯一的 `factors.parquet` 备份
  `factor_lab_data_backup_20261004/factors_20260929.parquet` 是**数据快照**，非配置快照。

### 1.8 项目纪律的适用范围

- **[已确认]** `windows.check_window()`（`windows.py:164-166`）规定：`evidence` 以 `E1`
  开头时 `end >= DECAY_MONITOR_START(2026-01-05)` 即判违规。
- **[推断]** 进化线窗口 `end = 2026-08-21` **必然被判违规**；
  但该函数**未被进化线调用**（1.1 已确认）。
  → 精确表述为：**项目宣称的全局窗口纪律未在进化搜索入口落实**（工程治理缺口），
  而非"进化搜索违反了已生效的正式规则"。是否构成正式违规需核对 PLAN 的适用范围与审批记录。
- **[待核实]** PLAN 中窗口纪律条文的**适用范围**是否明示覆盖个股线。

## 3. 关键结论

### 3.1 对三方意见的裁定

| 分歧点 | 各方主张 | 本审计裁定 | 依据 |
|---|---|---|---|
| 2026 能否作 E3 | DeepSeek：**能**，169 天可作 E3 | **不能**。Codex 第二轮修正正确 | §1.3、§2：169 天中 154 天已被消耗 |
| 是否立即改 `END` | DeepSeek：立即改为 2025-12-31 | **不同意立即改**。Codex 正确 | §1.7：来源未查明，改动会改变历史结果含义 |
| 2025 能否作新 F1 验证段 | DeepSeek：可以 | **不可以直接采用**。Codex 正确 | §2 区段 4：门控线已用作现行选择窗（76 条标签读取） |
| 2026 是否已被搜索消耗 | Codex 第二轮：已消耗 | **确认已消耗，且比 Codex 描述的更严重** | §1.3：不止读，月度结果已回写台账并进入 decision |
| 是否统一窗口**日期** | Codex：统一规则不统一日期 | **记录为待决**，但用户原则要求两端统一到 `≤2025-12-31` | 用户原则 + §1.1 两套窗口 |
| 进化线数据读取是否可追溯 | 三方均未直接验证 | **确认不可追溯**（无 boundary、无 git、台账仅 10 天） | §1.4 |

### 3.2 用户原则的可执行性

用户原则：**2026 年归最终部署；搜索 holdout 只能在 2025 年之前划分。**

- **[已确认]** 该原则**在 2021-2025 段完全可执行**：
  搜索段 `2021-09-01 ~ 2024-12-31`（或 `2021-06-01 ~ 2024-12-31`），
  内部 holdout 取该段尾部即可，不触及 2025 与 2026。
- **[已确认]** 该原则**对 2026 段只能"止损"，不能"追认"**：
  区段 5/6（154 交易日）已被消耗，**不得追认为独立 E3**。
- **[已确认]** 2025 全年（区段 3 尾 + 区段 4）**已被门控线用作现行选择窗**，
  也**不宜**直接充当独立性确认段；若要用，须先按 §4 的接触审计确认具体用途。

### 3.3 最严重的发现（排序）

1. **个股线数据读取无审计、无版本控制** —— 使一切"历史数据是否干净"的问题
   **在当前工程条件下不可判定**。这比 FDR 口径与 `END` 日期都更根本。
2. **2026 段的 91% 已被消耗且结果已展示** —— 直接摧毁"2026 作 E3"的可行性。
3. **两套窗口 + 两套纪律**，而文档宣称"单一事实源" —— 文档与代码不一致。
4. **`LEGACY_SEARCH_*` 命名指向错误对象** —— 审计常量本身不可信。
5. **`END=2026-08-21` 无依据可查** —— 生产常数来源不明。

## 5. 治理建议（本报告不含代码改动）

按"先保护、再审计、后动代码"的顺序：

| 优先级 | 措施 | 性质 | 依赖 |
|---|---|---|---|
| **P0** | 冻结 2026 数据访问权限：禁止任何**新的**搜索 / 筛选 / 调参 / 候选晋级读取 `date ≥ 2026-01-05` | 纪律（文档 + 入口检查） | 无 |
| **P0** | 固化现状：保存代码、配置、台账、候选清单、指标快照 | 工程 | 无（本报告 §1 已记录关键哈希） |
| **P1** | 完成 §4 的 7 项待核实 | 审计 | 无 |
| **P1** | 为个股线接入读取审计（`boundary.py` 或等价机制）与版本控制 | 工程 | 建议在 §4-1 之后 |
| **P2** | 按审计结果确定新搜索边界（目标：`≤2024-12-31`；holdout 在其内部） | 设计 | §4-1、§4-5 |
| **P2** | 在新划分下重建门控筛选—验证流程；原 `7/20` 保留为历史探索结果 | 设计 | §4-5 |
| **P3** | 冻结候选与规则，预先登记 E3 方案（样本量、期限、成功标准） | 设计 | P2 |
| **P3** | 从冻结之后产生的新数据开始保护 E3 | 纪律 | P3 |

**明确不做**：

- 不改 `fitness.py` 的 `START` / `END` / `HOLDOUT_START`（§4-1 未完成前）。
- 不把更晚的数据自动纳入旧实验。
- 不宣布存在任何历史的独立确认区间（§2 显示不存在）。
- 不采用未经论证的事后选择校正方法把探索结果包装成确认结论。
